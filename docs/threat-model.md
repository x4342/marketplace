# Marketplace threat model

## Scope and trust boundaries

The reviewed system is the private Go web process and worker, a PostgreSQL database, same-origin browser assets, and the deterministic payment and payout providers. The browsers, ordinary accounts, content moderators, finance administrators, database operators, reverse proxy, and any future provider have different trust levels. TEST units carry no real financial value. Production hosting, real providers, and external access are outside the rehearsed environment.

| Boundary | Data and possible failure | Current control and evidence | Residual exposure |
| --- | --- | --- | --- |
| Browser to application | Credential guessing, session theft or stale sessions, cross-site form submissions | Argon2id, opaque expiring sessions, one-use recovery codes, bounded authentication attempts, strict first-party cookies, same-origin checks, and form tokens. Identity integration covers expiry, recovery, logout and CSRF. | Availability under distributed abuse and an approved session-cookie setup behind the chosen endpoint require environment-specific review. |
| Account to account | Unauthorized access to private chats, order addresses, digital files, evidence, drafts, reviews or earnings | Participant or owner filters on protected routes, separately checked administrative roles, private pages served with `no-store`, and server-rendered escaped data. Integration suites exercise nonparticipant and wrong-role requests. | A participant can copy content they can legitimately access. Storage, retention, and audit access require approval. |
| Untrusted seller content | Invalid, oversized, or misleading listing images and private file content | One bounded listing upload. Bound JPEG, PNG and WebP uploads and decode dimensions, then crop, normalize and re-encode to JPEG. Digital test uploads accept bounded plain UTF-8 and use buyer-scoped attachment responses. | Production file formats, malware checks, quotas and private storage remain open. Public image metadata may appear in pixels intentionally supplied by a seller. |
| Applications to PostgreSQL | Replayed requests, stale writes, inconsistent journal entries, and data loss | Parameterized SQL, ownership checks, transactional state changes, unique event keys, per-seller fund locking, and database journal and history constraints. Restore and reconciliation exercise populated PostgreSQL fixtures. | The database owner can bypass application controls. Production grants, backup keys, recovery targets, and write access to operator tools need independent review. |
| Staff to moderation and finance | Conflicts of interest and unauthorized category of action | The centralized effective role distinguishes users, combined moderators, and platform administrators. Every sensitive financial mutation requires fresh password confirmation. Moderators cannot decide their own case. Appeals require independent review. Sensitive staff reads and decisions are audited where provided by M6–M8. | Staff can still misuse legitimately assigned access. Provisioning, rotation, incident ownership, and any dual-control requirement need approval. |
| Provider and network boundary | False payment or payout confirmation, duplicate callbacks, correlation, and interrupted requests | Simulated providers, checked asset/network and quote values, idempotent transactional posting, no remote assets, and essential forms usable without JavaScript. Onion responses retain same-origin form headers while the cross-origin and form-token checks continue to apply. | Real provider authentication, finality, payout controls, the selected launch topology and Tor Browser compatibility need separate review. |

Review the threat model if any new provider, upload format, public endpoint, storage processor, proxy, or administrative role changes these boundaries.

M13 requires the administrator capability for system status, user and role queries, category editing, and platform audit. Staff keep their moderation and finance scopes. Role writes serialize with bootstrap and enforce an administrator floor. Category writes use CSRF, confirmation, a current revision, integrity checks, and immutable actor attribution. Public discovery retains its read-only category views.

M14 public member search returns only profile-visible fields and excludes restricted accounts. Direct conversation creation is CSRF-protected, pair-unique and bounded per account. Thread reads, previews, sends, reports and participant controls remain private. A new database guard requires the exact verified order's listing conversation and snapshot for purchase event insertion. Browser storage holds only the workspace disclosure preference.
